### §0 왜 이 SPEC인가 — 관통 명제

**「완주율 12%」는 학생이 그만둔 비율이 아니라 완주 기록이 살아남은 비율이다.**

2026-08-25에 라이브를 재다가 드러났다. 리포트는 완주를 `done` 플래그로 세는데, **그 플래그가 코드 경로 하나에 의해 규칙적으로 지워진다.**

1. 최종 리포트 화면이 열리면 `recordSemesterDone()`이 `done:true` 레코드를 PUT한다 (`11-report.js:623`)
2. 그 뒤 학생이 탭을 닫거나 태블릿을 전환하면 `pagehide`·`visibilitychange:hidden`이 `_ltRecordLeave()`를 부른다 (`08d-log-transmit.js:71`)
3. 그 함수는 **학기 완주 여부를 보지 않는다.** 보는 것은 `entered`(시나리오에 들어간 적 있나) 하나뿐이고, 완주자는 당연히 통과한다 → `makePlayRecord(gs,{done:false})`를 다시 PUT
4. 수집 Lambda의 키가 `raw/{v}/{yyyy}/{mm}/{dd}/{pid}.json`이라 **같은 판은 같은 파일을 덮어쓴다**

**→ 리포트를 끝까지 보고 창을 닫는 가장 모범적인 플레이가 정확히 이 경로를 탄다.**

#### 실측 근거 (2026-08-25 17:00 KST, 라이브)

- `GET /stats` — 총 **153판** · 마지막 유입 `2026-08-25T03:37:35Z` · r42 실사용 **129건**(mid 104 · elem 25)
- `GET /report` — 완주 **18** · 완주율 **12%**
- 그런데 **깔때기가 거의 안 좁아진다** (중등 5종, 잠금 해제 순서):
  `selfintro 122 → groupwork 102 → eorinwangja 100 → career 96 → studyplan 97`
  첫 관문에서 한 번 줄고 그 뒤로는 평평하다. **다섯 개를 다 끝낸 사람이 100명 가까이 된다.**

#### 무엇이 남고 무엇이 사라졌나

덮어쓰는 레코드도 `makePlayRecord`가 매번 `gs.scenarioHistory`에서 **다시 만든다.** 그래서 `sc`는 온전하다.

| 살아남는다 (`sc[]`) | 사라진다 (`end`) |
|---|---|
| `id` 시나리오 · `g` 등급 · `s` 최종점수 | `total` 총점 |
| `t1`·`t2`·`rv` 1차/2차/검토 선택 | `lv` 레벨 |
| `dur` 소요초 · `rep` 재도전 횟수 | `type` 학습자 유형 |
| `gs[]`·`du[]` **시도별** 등급·시간 | `cards` 수집 카드 |
| `dl`·`dk` 델타 · `ct`·`ce` 자원 소비 · `cd` 할인 | (`done` 플래그도 같이) |

**→ 「어디까지 갔고 무엇을 골랐나」는 통째로 살아 있다.** 그러므로 **판정을 플래그에서 데이터로 옮기면 지금 쌓인 것으로 진짜 숫자가 나온다.** 클라이언트를 고치지 않고도.

#### 이 SPEC이 «안» 하는 것

- **클라이언트 수정(r43)은 이 SPEC 밖이다.** `_ltRecordLeave`가 완주한 판을 덮지 않게 하는 것은 학교 배포본 재빌드라 되돌리기 비용이 다르다. **새는 양을 숫자로 안 뒤에 판단한다.**
- 그때까지 라이브는 깨진 것이 아니다 — **집계 숫자만 실제보다 낮게 나오는 상태**다.

### §1 판정 재정의 — `DONE-0xx`

**DONE-010** — 완주를 두 기준으로 «동시에» 낸다. 한쪽으로 갈아치우지 않는다.
- `flagged` = `rec.done === true` (기존 기준, 그대로 보존)
- `full` = `sc[]`가 **그 버전의 시나리오 세트를 전부 포함**

**DONE-020** — 버전별 시나리오 세트는 서버가 모르므로 표로 박는다. 판정은 `rec.v`의 접두사로 한다.

| 접두사 | 세트(잠금 해제 순서) |
|---|---|
| `v1.3-mid` | `selfintro` · `groupwork` · `eorinwangja` · `career` · `studyplan` |
| `v1.4-mid` | 위와 같음 (**구현 때 추가** — `v14/src/js/00-config.js:31`이 같은 세트로 이미 존재한다. 라이브 유입은 아직 0건이지만, 표에 없으면 그 버전이 폴백으로 새서 완주가 틀리게 잡힌다) |
| `v1.3-elem` | `bookreport` · `animaltalk` · `jobcard` · `classmascot` · `historycheck` |
| 그 밖 | 폴백 = `sc.length >= 5` |

✅ **2026-08-25 코드 대조 완료** — 세 행 전부 클라이언트 `00-config.js`의 `scenarios` 배열과 글자까지 일치(`v13-mid:38` · `v13-elem:38` · `v14:31`). 라이브 `rec.v`는 `v1.3-mid-r42` 꼴이라 접두사 판정이 맞는다(`/stats` byVersion 실측).

⚠️ 이 표는 클라이언트 `00-config.js`의 `scenarios`에서 왔다. **거기가 바뀌면 여기도 바뀌어야 한다** — 표 옆에 그 사실을 주석으로 박는다(값의 뜻을 바꾸면 설명하는 것을 전부 센다).

**DONE-030** — 화면에 **둘을 나란히** 놓고, 차이를 이름 붙여 명시한다.
> `기록상 완주 {flagged}` · `실제 완주 {full}` · **`계측 손실(하한) {full - flagged}`**

「하한」인 이유 = `full`도 놓치는 경우가 있다(마지막 시나리오 도중에 떠난 사람은 `sc`에도 안 들어간다). **조용히 한 숫자만 보여주지 않는다.**

**DONE-040 — 유효 판 정의.** 기본으로 아래를 제외하고, 상단에 「제외 N건」을 적는다. `?all=1`이면 포함.
- `rec.v`가 `v0-e2e-test`이거나 `-selftest`로 끝나는 것 (우리 시험분)
- `sc.length === 0`인 판은 **제외하지 않고 「진입만」 구간으로 따로 센다.** 화면을 열었지만 시나리오를 하나도 안 끝낸 사람이고, 그 수 자체가 첫 관문의 신호다

### §2 화면 — `VIZ-0xx`

기존 `/report` HTML 한 장을 유지하되 구획을 더한다. **JSON이 아니라 브라우저로 여는 화면이다**(§12 원칙 유지). `?format=json`은 그대로.

**VIZ-010 상단 카드 — 네 개로 교체**
`전체 판` · `실제 완주(full)` · `기록상 완주(flagged)` · `계측 손실(하한)`
완주율은 **`full` 기준**을 크게, `flagged` 기준을 그 아래 작게.

**VIZ-020 ★진짜 깔때기 (신규, 이 화면의 중심)**
버전 세트 순서대로 「여기까지 끝낸 판 수」를 단계별로 낸다. 각 단계에 **직전 대비 유지율**을 붙인다.
```
진입만  →  1개  →  2개  →  3개  →  4개  →  5개(완주)
```
- 중등·초등을 **따로** 그린다(세트가 다르므로 합치면 뜻이 없다)
- 각 막대에 절대수와 %를 같이. 막대는 CSS만으로 그린다(외부 라이브러리 금지 — 인라인 Lambda다)

**VIZ-030 멈춘 자리 — 두 층으로 가른다**
지금 「어디서 멈췄나」는 `cur`만 보는데, `cur`는 **시나리오 «안»에서 떠났을 때만** 찍힌다(설계다, 버그가 아니다). 그래서 121건이 원리상 안 잡혔다.
- **층 A — 시나리오 «사이»에서 멈춤**: `sc[]`의 **마지막 원소** 기준 집계. 미완주 대다수가 여기 잡힌다
- **층 B — 시나리오 «안»에서 멈춤**: 기존 `cur.id / cur.step` 집계 (지금 화면 그대로)
- 두 층의 합이 미완주 총계와 맞는지 **화면에 검산 줄**을 둔다. 안 맞으면 그 차이를 그대로 적는다

**VIZ-040 재도전 궤적 (신규)**
`gs[]`(시도별 등급)·`du[]`(시도별 소요)가 있는 판만. 「1회차 → 최종」 등급 이동을 시나리오별로 낸다. **수업에서 제일 쓸 만한 숫자다** — 다시 하면 나아지는가에 직접 답한다.

**VIZ-050 소요 시간 분포 (신규)**
지금은 중앙값 하나뿐. **분포(구간별 히스토그램)**를 더한다. 수업 시간 설계에 쓰는 숫자는 중앙값이 아니라 꼬리다.

**VIZ-060 보존** — 버전별 · 시나리오별(플레이·평균점수·등급 분포) · 선택 분포 · 학습자 유형은 지금 그대로 둔다.
⚠️ **학습자 유형은 `end`에서만 나오므로 덮인 판에선 영영 없다.** 그 구획 제목 옆에 **「완주 기록이 남은 N건만」**을 적어, 표본이 전체가 아님을 화면이 스스로 말하게 한다.

### §3 이벤트 파이프 관측 — `EV-0xx`

r42부터 게임이 `POST /log-ev`로 풀 이벤트 스트림을 보낸다(`08e-verbose-log.js`, `CONFIG.verboseLog:true`). **그런데 도착 여부를 밖에서 볼 창구가 없다** — `/stats`가 `Prefix:'raw/'` 하드코딩이고 조회 역할도 `raw/*`에만 붙어 있다.

**EV-010 `GET /stats-ev` (신규, 싸다)**
`raw-ev/` prefix를 `ListObjectsV2`로 순회. **GetObject 안 한다.**
- 응답: `{ total, byVersion, pids, latest }` — `pids`는 키에서 뽑은 **고유 판 수**(키 문법 `raw-ev/{v}/{yyyy}/{mm}/{dd}/p_{...}__{part}.ndjson`, part 롤오버가 있어 파일 수 ≠ 판 수)
- 권한: 조회 역할에 `raw-ev/*` `ListBucket` 한 줄 추가. **쓰기는 안 준다**
- ⚠️ `raw/*`와 `raw-ev/*`는 prefix가 슬래시까지라 서로를 포함하지 않는다(템플릿 주석 §209에 이미 적혀 있다)

**EV-020 `semester_report_viewed` 집계 — 기본 off**
12%의 실체를 가르는 유일한 신호다. **「덮어써서 안 보이는 것」과 「진짜로 리포트까지 안 간 것」이 A 파이프에서는 똑같은 모양(`sc` 5개 + `done:false`)으로 남는다.**
- `/report?ev=1`일 때만 동작. **기본은 끈다**(GetObject 비용)
- 리포트 역할에 `raw-ev/*` `GetObject`+`ListBucket` 추가
- 판별로 이벤트를 읽어 `semester_report_viewed`가 있는지 **불리언 하나만** 뽑는다. 이벤트 본문은 화면에 안 싣는다
- 상한 = `MAX_EV_RECORDS`(기본 2,000). 넘으면 **상단 배너로 명시한다 — 조용히 자르지 않는다**
- 결과를 VIZ-010 옆에 셋째 기준으로 놓는다: `리포트 도달(ev) {N}`

**EV-030 세 숫자가 답하는 것**
| | 뜻 |
|---|---|
| `full` (sc 5개) | 다섯 시나리오를 다 끝냈다 |
| `ev` (semester_report_viewed) | 최종 리포트 화면까지 갔다 |
| `flagged` (done:true) | 그 기록이 덮이지 않고 살아남았다 |

`full > ev` = 「목록으로」를 안 눌러 리포트가 안 열린 사람 (UI 흐름 문제)
`ev > flagged` = **덮어쓰기로 잃은 양** (r43 판단의 근거)

### §3.5 SPEC 이후 구현에서 더한 것 (2026-08-25)

선문에 없던 것을 코드가 하고 있으면 다음 사람이 SPEC을 근거로 읽다 틀린다. 넷을 여기 적는다.

- **`?all=1`** — DONE-040이 「`?all=1`이면 포함」이라고만 적고 파라미터를 정의하지 않았다. 구현: 시험분 제외를 끄는 스위치. 켜지면 상단 meta에 `?all=1 (시험분 포함)`을 굵게 표시한다
- **소요 p90 열** — VIZ-050이 「꼬리」를 말하면서 히스토그램만 시켰다. 시나리오별 표에 `소요(p90)` 열을 더해 히스토그램과 같이 읽게 했다
- **`StatsEvFunction`이 `StatsExecutionRole`을 함께 쓴다** — EV-010이 「조회 역할에 한 줄 추가」라 했으므로 역할을 새로 만들지 않았다. 새 역할 = 새 IAM 리소스 = 되돌릴 것이 하나 더 는다
- **`/stats-ev`가 `pids`와 `pidsBootstrap`을 갈라서 낸다** — EV-010은 `pids` 하나만 시켰는데, `08e-verbose-log.js` §3-2의 **pid 회전** 때문에 `p_b…` 부트스트랩 파일이 섞여 있다(playId 발급 전 구간이라 판과 1:1이 아니다). 합쳐 세면 판 수가 부풀어 보인다

> ⚠️ **선문에서 틀렸던 것 하나** — §6에 「인라인 Lambda라 외부 라이브러리 금지」의 근거로 크기를 걱정했는데, `AWS::Lambda::Function` `Code.ZipFile`의 실제 상한은 **압축 4MB**다(문자 4,096이 아니다 — AWS 문서 확인). 리포트 코드가 7,955자에서 **17,251자**로 늘었지만 상한과는 무관하다. 외부 라이브러리를 안 쓰는 이유는 크기가 아니라 **인라인에는 `node_modules`를 넣을 수가 없어서**다(SDK만 런타임에 있다).

### §5 검증 — `VER-0xx`

⚠️ **자기보고를 안 믿는다.** 배포 전에 아리공이 닫을 수 있는 것은 전부 닫는다.

**VER-010 — 코드 문법**: 템플릿에서 인라인 Lambda를 뽑아 `node --check`. **다섯 전부**(stats-ev 신설로 넷→다섯).

**VER-020 — 스텁 집계**: S3 클라이언트를 스텁으로 갈아끼우고 **실제 레코드 모양**으로 돌린다. 최소 이 다섯 케이스를 손으로 만든다.
1. `sc` 5개 + `done:true` → full ○ / flagged ○
2. `sc` 5개 + `done:false` (**덮인 완주**) → full ○ / flagged ✗ ← **이번 개정의 핵심 케이스**
3. `sc` 3개 + `done:false` → full ✗, 층 A의 「3번째 시나리오」에 잡힘
4. `sc` 2개 + `cur` 있음 → 층 B에 잡힘
5. `sc` 0개 → 「진입만」
6. `v0-e2e-test` → 기본 조회에서 제외, `?all=1`에서 포함

**VER-030 — 검산 줄**: 층 A + 층 B + 완주 + 진입만 = 유효 판 총계. **화면에 그대로 낸다.** 안 맞으면 차이를 적는다.

**VER-040 — 회귀**: 기존 §12 구획(버전별·시나리오별·선택 분포)이 개정 전후로 **같은 수를 낸다.** 판정 하나를 더한 것이지 기존 집계를 바꾼 게 아니다.

**VER-050 — 라이브 대조**: 배포 후 `/report`를 실제로 열어 `flagged`가 **18**로 나오는지 본다. 안 나오면 개정이 기존 집계를 건드린 것이다.

**VER-060 — 미리보기 산출물**: 배포 전에 스텁 데이터로 HTML을 뽑아 **피터공이 5초에 판정할 형태**로 올린다. 화면을 보고 구획을 가감한 뒤 배포한다.
