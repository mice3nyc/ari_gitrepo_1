# SPEC — spec-guard (선문후코 실시간 강제 훅)

> 구현: `spec_guard.sh` · 짝: `drift_scan.sh` · 정본: `_dev/개발 방법론 — 선문후코.md` ④ 강제
> 개정: 2026-08-18 — Bash로 만든 파일을 못 보던 구멍을 막는다.

## 1. 역할

`_dev`/`_devhaus` 하위 **코드 파일이 그 프로젝트의 최신 SPEC보다 새로우면**
「SPEC에 반영했나」를 아리공 눈앞에 주입한다. **차단이 아니라 경고**다(exit 0 + additionalContext).

조건에 안 걸리면 조용히 `{}`를 낸다. 대부분의 편집에는 아무 소음이 없어야 한다.

## 2. 2026-08-18 개정 — 왜 고치는가

**구멍**: 훅 matcher가 `Edit|Write`였고, 가드는 `.tool_input.file_path`만 읽었다.
그래서 **Bash로 만든 파일은 아예 보이지 않았다.**

실제로 터졌다(세션 920, 인생게임). 그날 만든 스크립트 5개를 전부 Bash 히어독(`cat > …`)으로 썼고
훅은 **한 번도 발화하지 않았다.** 같은 세션에 `pages/game.vue`를 Edit로 고쳤을 때는 정상 발화했다.
결과로 카드 생성기가 SPEC 없이 커밋됐고, 세션 마감 감사에서야 드러났다.

> **교훈**: 「규칙을 안 지켰다」가 아니라 **「게이트가 안 보는 경로로 파일이 생겼다」**다.
> 이 세션 설정은 Bash 우선으로 일하게 되어 있어서, 안 고치면 같은 구멍이 계속 열린다.

## 3. 설계 결정 — 명령줄을 파싱하지 않는다

Bash 호출에서 «어느 파일이 쓰였는가»를 알아내는 길이 둘이다.

- **(가) 명령줄 파싱** — `>`·`>>`·`tee`·`cp`·`mv`·`sed -i`에서 대상 경로를 뽑는다.
- **(나) 최근 변경 스캔** — 방금 바뀐 코드 파일을 파일시스템에서 찾는다.

**(나)를 쓴다.** 결정적인 이유: 이번 구멍을 실제로 만든 것은 `python3 - <<PY` 안의 `open(p,'w')`였고,
**거기엔 리다이렉트도 경로도 명령줄에 나타나지 않는다.** 파서였다면 원인이 된 바로 그 케이스를 놓쳤다.
빌드 스크립트·생성기·포매터처럼 «명령은 짧고 쓰기는 안에서 일어나는» 것이 앞으로도 다수다.

**비용 — 프루닝 목록이 성능을 결정한다.** `-newermt`는 트리의 파일을 전부 stat하므로,
대상 수가 곧 비용이다. 실측(2026-08-18, 이 볼트):

| 프루닝 | 남는 파일 | 호출당 |
|---|---:|---:|
| `.git`·`node_modules`만 | 38,456 | — |
| + `.nuxt`·`.output`·`dist`·`build`·`target`·`Pods`·`.next`·`coverage`·`venv` | 17,091 | **145ms** |
| + **`.build`**(Swift 빌드 산출) | 4,897 | **38ms** |

`.build` 하나가 12,000개였다(myscribe). **프루닝은 선택이 아니라 전제다** —
새 언어·툴체인이 들어오면 그 산출 폴더를 목록에 더한다. 훅 timeout은 5s라 여유는 크지만,
매 Bash 호출에 도는 비용이라 자릿수가 바뀌면 체감된다.

## 4. 동작

```
tool_name = Edit | Write  → .tool_input.file_path 를 대상으로            (기존 그대로)
tool_name = Bash          → _dev·_devhaus에서 최근 SCAN_WINDOW 초 안에
                            변경된 코드 파일 중 가장 새것을 대상으로     (신설)
그 외                      → 조용히
```

대상이 정해진 뒤의 판정은 **양쪽이 같은 함수를 쓴다.** 두 벌로 두면 갈라진다.

1. `_dev`/`_devhaus` 하위인가 → 아니면 조용히
2. 코드 파일인가(`docs/`·`.md`·`.json`·설정류 제외) → 아니면 조용히
3. 프로젝트 루트의 `docs/SPEC*.md` + 루트 `SPEC*.md` 중 최신 mtime
4. SPEC이 하나도 없으면 → 「SPEC부터 세우라」
5. 코드 mtime > 최신 SPEC mtime이면 → 「SPEC에 반영했나」

## 5. 같은 경고를 반복하지 않는다

Bash 경로는 **부수적으로** 걸린다. 파일 하나가 SPEC보다 새 상태로 남아 있으면
그 뒤의 모든 `ls`·`grep`·`git status`가 같은 경고를 다시 낸다 — 컨텍스트가 경고로 찬다.

그래서 **`{경로}:{mtime}` 한 쌍당 한 번만** 낸다(상태 파일 `SCAN_STATE`).
mtime이 바뀌면(= 파일을 또 고쳤으면) 다시 낸다. 그래서 진짜 새 변경을 삼키지는 않는다.
Edit/Write 경로에도 같은 규칙을 건다 — 편집마다 mtime이 바뀌므로 억제되는 일이 없다.

## 6. 상수

| 이름 | 값 | 이유 |
|---|---|---|
| `SCAN_WINDOW` | 120초 | 긴 빌드·생성기가 끝난 뒤에 훅이 도는 경우를 덮는다 |
| `SCAN_STATE` | `/tmp/spec_guard_seen` | 재부팅으로 비워져도 무해(다시 한 번 경고할 뿐) |

## 7. 검증 (고치기 전 붉은 것을 먼저 본다)

`_dev/spec-guard/selftest.sh` — 픽스처로 가짜 프로젝트를 만들어 가드에 JSON을 먹인다.

1. **개정 전 재현**: Bash로 만든 코드 파일 → 옛 가드는 `{}`(구멍). ← 이게 붉게 떠야 한다
2. Bash로 만든 코드 파일 → 새 가드는 경고
3. 같은 파일 두 번째 호출 → 조용(중복 억제)
4. 파일을 또 고치면 → 다시 경고
5. SPEC이 코드보다 새로우면 → 조용
6. SPEC이 아예 없으면 → 「SPEC부터」
7. `docs/`·`.md` 편집 → 조용
8. `_dev`·`_devhaus` 바깥 → 조용
9. Edit/Write 경로가 개정 전과 같게 동작하는가(회귀)

**0건 통과를 통과로 세지 않는다** — 각 케이스가 «기대한 문자열»을 실제로 냈는지 본다.
